# 사용(출고) 이력 수정·삭제 설계

행을 두 번 클릭하면 팝업이 열려 출고 이력을 고치거나 지울 수 있게 합니다.
자재 목록이 이미 쓰는 방식과 같은 모양입니다.

작성: 2026-08-18

---

## 왜 필요한가

지금은 한 번 등록한 출고를 고칠 방법이 없습니다. 오타나 잘못 고른 자재를 바로잡으려면
DB를 직접 건드려야 합니다.

## 무엇을 정했나

사용자와 확인한 결정입니다. **바꾸려면 여기부터 다시 이야기해야 합니다.**

| 항목 | 결정 |
|---|---|
| 고칠 수 있는 범위 | **전부** — 일자·자재·출처·수량·설비ID·문제·조치·부품메모·비고 |
| 삭제 | **가능** |
| 권한 | **관리자만** (일반은 공용 계정을 여럿이 써서 책임 추적이 안 됨) |
| 수리 반납이 등록된 건 | **수정·삭제 금지.** 반납을 먼저 취소하게 안내 |
| 수리 건이 없던 옛 이력 | **수리 건을 새로 만들지 않음.** 재고만 규칙대로 조정 |
| 비한진 → 한진으로 바꾼 경우 | **수리 건을 새로 만듦** (2026-08-18 추가 결정) |

---

## 1. 왜 DB 함수가 필요한가

자재나 출처를 바꾸면 재고가 두 군데서 움직입니다.

```
자재 A -> B      A 재고 += 옛 수량,  B 재고 -= 새 수량
출처 한진 -> 보우  재고를 되돌리기만 (보우 자재는 안 깎으므로)
수량 1 -> 3      차이 2 만큼 더 깎기
```

여기에 수리 건 처리까지 붙습니다. 화면에서 여러 번 나눠 부르면 중간에 통신이 끊겼을 때
**재고만 바뀌고 이력은 그대로**인 상태가 생깁니다. 그래서 DB 함수 하나로 묶습니다.
출고 등록(`register_usage`)과 구매요청 삭제(`remove_purchase_request`)가 쓰는 방식과 같습니다.

## 2. `repairs`에 `history_id` 추가

**지금 `register_usage`는 수리 건을 만들면서 출고 이력과의 연결 고리를 안 남깁니다.**
그래서 나중에 "이 출고가 만든 수리 건이 어느 것인지" 알 수 없습니다.

자재·수량·날짜로 추측할 수는 있지만 안 됩니다. **같은 날 같은 자재를 같은 수량으로 두 번
출고한 기록이 실제로 있습니다**(2026-06-22 `Tail DRUM(Φ89 1150W용 B/F 1050)` 2건).
추측하면 엉뚱한 수리 건을 지웁니다.

```sql
alter table repairs add column history_id bigint references history (id) on delete set null;
create index idx_repairs_history_id on repairs (history_id);
```

**지금 넣기 좋은 시점입니다.** `repairs`에는 소급이관한 대여반납 168건과 웹앱 등록 2건뿐이고,
`history` 4,457건은 대부분 직접 넣은 것이라 수리 건이 아예 없습니다. 기존 건은 비어 있어도
실질적인 문제가 없고, 앞으로 등록되는 것부터 이어집니다.

## 3. `register_usage` 수정

**함수 이름과 인자는 그대로 둡니다.** 시그니처가 바뀌면 브라우저에 캐시된 옛 화면을 쓰는
사람이 등록을 못 하게 됩니다(`시스템_규칙과_배경.md` 참고). 안쪽만 고칩니다.

```sql
insert into history (...) values (...) returning id into v_history_id;
...
insert into repairs (material_id, quantity, sent_on, reason, note, history_id)
values (..., v_history_id);
```

## 4. 차감 여부 판단 함수

"한진 자재만 깎는다"는 규칙이 지금 화면(`usage.js`의 `MATERIAL_SOURCES`)에만 있습니다.
이력을 고치려면 **예전 출처가 깎였는지**를 DB가 스스로 알아야 합니다.

```sql
create or replace function usage_deducts_stock(p_manager text) returns boolean
language sql immutable as $$
    select p_manager in ('한진 SPARE', '한진 구매품');
$$;
```

> ⚠️ **규칙이 화면과 DB 두 군데에 생깁니다.** 한쪽만 고치면 어긋납니다.
> 이 규칙은 두 번 뒤집혔던 이력이 있습니다(`시스템_규칙과_배경.md` 1절).
> 양쪽 주석에 서로를 가리키는 경고를 달고, 아래 [10-2] 검사가 어긋남을 잡습니다.

## 5. `update_usage`

```
0. history 행을 select ... for update 로 잠그기   (아래 '동시 수정' 참고)
1. 관리자인지 확인                        아니면 거부
2. 수량이 1 이상인지                      아니면 거부
3. 이 출고의 수리 건에 반납이 있나         있으면 거부
4. 옛 상태 되돌리기
     옛 출처가 한진이면  옛 자재 재고 += 옛 수량
5. 수리 건 처리 (history_id 로 찾음)
     있고  새 상태가 한진   -> 자재·수량·일자를 새 값으로 갱신
     있고  새 상태가 비한진  -> 삭제
     없고  비한진 -> 한진   -> 새로 만듦 (실수로 보우로 등록했다 고치는 경우)
     없고  한진 -> 한진     -> 아무것도 안 함 (이관분이 여기. 새로 만들지 않음)
6. 새 상태 적용
     새 출처가 한진이면  새 자재 재고 -= 새 수량
7. history 행을 새 값으로 수정
```

**자재를 비운 채로 저장할 수 있습니다.** 2026-07 이관분처럼 `material_id`가 없는 행에서
설비ID 오타만 고치고 싶을 때, 자재를 억지로 지정하게 하면 안 됩니다.
`material_id`가 `NULL`이면 4번과 6번의 재고 갱신이 0행에 걸려 **아무 일도 일어나지 않습니다.**

**동시 수정 — 0번이 필요한 이유.** 관리자 둘이 같은 행을 동시에 고치면, 둘 다 "옛 수량 1"을
읽고 각자 재고를 +1 되돌려 **2가 늘어납니다.** 행을 잠그면 뒤에 온 쪽이 앞의 결과를 보고
계산합니다. 이 저장소는 동시성 문제로 여러 번 고생한 이력이 있습니다
(`repairs.js`의 반납 처리, `usage.js`의 불러오기 순번).

## 6. `delete_usage`

```
0. history 행을 select ... for update 로 잠그기
1. 관리자인지 확인
2. 반납이 있으면 거부
3. 옛 출처가 한진이면  재고 되돌리고, 딸린 수리 건이 있으면 삭제
4. history 행 삭제
```

## 6-1. 실행 권한

두 함수 모두 로그인한 사람에게 열어주고, **관리자 확인은 함수 안에서** 합니다.
`register_usage` 등 기존 함수와 같은 방식입니다.

```sql
grant execute on function update_usage(...) to authenticated;
grant execute on function delete_usage(bigint) to authenticated;
```

> 권한 검사를 함수 밖(화면)에만 두면 안 됩니다. RPC는 로그인한 사람 누구나 직접
> 부를 수 있습니다. `register_usage` 주석에 같은 경고가 적혀 있습니다.

## 7. 화면

### 7-1. 표에 더블클릭

```javascript
renderTable(TABLE_ID, history, COLUMNS, {
    selectable: true,
    onRowClick: (row) => { ... },                                  // 지금 있는 BOQ 이동 (그대로)
    onRowDblClick: isAdmin ? (row) => openDialog(row.id) : null,   // 추가
});
```

한 번 클릭은 지금처럼 BOQ 이동, 두 번 클릭이 수정 팝업입니다.

### 7-2. `getUsageHistory`에 번호 추가

지금 이 함수는 행 번호를 안 돌려줍니다. 어느 행을 고칠지 알 수 없으므로 `id`와
`material_id`를 추가합니다. 표에는 안 보이게 합니다(`COLUMNS`에 안 넣음).

### 7-3. 팝업 `usage-dialog`

`index.html`에 `mat-dialog`와 같은 모양으로 만듭니다. 부품·출처 선택칸은 출고 등록 폼에
이미 있는 `fillPartOptions` / `fillSourceOptions`를 그대로 재사용합니다.

```
일자 / 부품명(카테고리로 좁히기 포함) / 자재 출처 / 수량 /
설비ID / 문제 / 조치 / 부품메모 / 비고
[저장]   [삭제] ☐ 확인했습니다
```

### 7-4. 재고가 어떻게 바뀌는지 미리 보여주기

값을 바꿀 때마다 실시간으로 갱신합니다.

```
수량 1 -> 3       'PVC Belt L=1,233 W=157' 재고가 2개 줄어듭니다 (10 -> 8)
출처 한진 -> 보우   재고가 1개 늘어납니다 (10 -> 11) / 수리 관리에서 사라집니다
자재 A -> B       'A' +1 / 'B' -1
```

음수가 되면 빨간 글씨로 경고하되 **막지는 않습니다**(음수를 허용하기로 한 기존 방침).

### 7-5. 안전장치

- **삭제는 체크박스를 켜야** 눌립니다 (자재 목록과 같음)
- **반납된 건**은 팝업을 열자마자 저장·삭제를 잠그고 안내합니다
  > 이 출고는 수리 반납이 등록되어 있어 고칠 수 없습니다. 수리 관리에서 반납을 먼저 취소하세요.
- **자재 연결이 없는 옛 이력**(2026-07 이관분 4,244건)은 안내합니다
  > 이 기록은 자재가 연결돼 있지 않습니다. 자재를 지정하면 그 자재의 재고에서 빠집니다.
- 저장 뒤 표를 다시 읽고, 재고가 음수면 알립니다
- `audit_log`에 남깁니다 (자재 수정과 같이 화면에서 `insertAuditLog` 호출)

## 8. 검증 — `verify_stage3.py`에 추가

기존 검사처럼 **임시 자재를 만들어 그것으로만 시험하고 끝나면 지웁니다.**

**[10] 출고 수정**

| | 검사 |
|---|---|
| 10-1 | 수량만 바꾸면 재고가 차이만큼 반영되는가 (1 -> 3 이면 재고 -2) |
| 10-2 | 출처를 한진 -> 보우로 바꾸면 재고가 원복되고 수리 건이 사라지는가 |
| 10-3 | 자재를 A -> B로 바꾸면 A는 늘고 B는 줄어드는가 |
| 10-4 | 반납이 등록된 건은 수정이 거부되는가 |
| 10-5 | 수량 0 이나 음수는 거부되는가 |
| 10-6 | ★ 일반 권한으로는 수정이 막히는가 |

**[11] 출고 삭제**

| | 검사 |
|---|---|
| 11-1 | 삭제하면 재고 원복 + 수리 건 삭제 + 이력 삭제가 한 번에 일어나는가 |
| 11-2 | 반납이 등록된 건은 삭제가 거부되는가 |
| 11-3 | ★ 일반 권한으로는 삭제가 막히는가 |

★ 두 개가 특히 중요합니다. 나머지는 관리자로만 돌리면 권한 방어가 통째로 사라져도
전부 통과합니다. **일반 계정 로그인을 건너뛰면 이 검사가 빠집니다.**

## 9. 되돌리기

컬럼 추가와 함수 추가라 되돌리기가 쉽지 않습니다. 컬럼은 그냥 둬도 무해하지만,
**이미 수정·삭제한 이력은 원상복구가 안 됩니다.** 검증을 통과시킨 뒤 배포합니다.

## 10. 하지 않는 것

- **수정 이력(누가 언제 무엇을 바꿨는지)을 따로 표로 보여주기** — `audit_log`에 남기는
  것까지만 합니다. 조회 화면은 요청이 없었습니다.
- **일반 권한에게 글자만 고치게 열어주기** — 관리자만으로 정했습니다.
- **`material_id`가 빈 4,244건을 채우는 작업** — 별개 과제입니다
  (`자재이관_주의사항.md` 9절 참고).
